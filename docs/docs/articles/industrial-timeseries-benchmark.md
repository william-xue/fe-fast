# 工业时序曲线：一次 Canvas 与 ECharts 的对照实验

<div class="meta">
  <span>2026-10-21</span><span>·</span>
  <a href="../bench/" target="_blank" rel="noreferrer">在线演示</a>
</div>

这个实验把三种曲线渲染方式放在同一个页面里：每批数据都交给 ECharts、裁剪窗口后再交给 ECharts，以及自己用 Canvas 画。想比较的是，历史数据变多以后，每次刷新还需要处理多少数据。

数据由浏览器本地生成，共六路信号，模拟有功、无功、频率、电压、油温和 SOC。历史跨度三小时，总点数可以选十万、三十万或一百万，启动后每 50ms 追加一批。它没有接真实设备，也没有验证生产环境的网络和长时间运行情况。

## 三种写法分别做了什么

| 实现 | 实时更新方式 |
|---|---|
| ECharts 朴素版 | 保留全部点，每批调用一次 `setOption`，传入完整序列 |
| ECharts 调优版 | 裁掉窗口外的点，开启 LTTB、关闭动画，用 rAF 合并刷新 |
| Canvas 版 | 环形缓冲存原始点，按可视窗口聚合成像素列，再绘制曲线 |

“一百万点”指六路历史数据的总量。默认窗口只有 60 秒，实时模式并没有把三小时的全部历史都画在屏幕上。“回看全历史”会把窗口拉到整段数据，这是另一种负载，页面里单独测。

Canvas 版也少了通用图表库的很多能力，目前只有滚轮缩放和十字光标。这里比较的是这些具体实现，不能据此给两个技术排一个通用名次。

## Canvas 把工作放到了哪里

原始数据放在固定容量的环形缓冲里。时间用 `Float64Array`，数值用 `Float32Array`；写满后覆盖最旧的点。这减少了逐点对象分配，但也意味着旧历史会被淘汰，需要长期查询的数据还得另存。

绘制前，把可视时间范围切成若干列，一列对应一个 CSS 像素。每列保留 `min / max / first / last`，绘制时使用这些聚合值，而不是遍历每一个原始点。保留极值是为了让尖峰参与绘制；列里的采样顺序仍然被压缩了，不能拿聚合后的曲线替代原始数据分析。

这省下的是绘制路径的工作量。缩放或改变窗口时，`_layoutScale` 仍会读取窗口内的原始点，重建列栅格。

三层 Canvas 分别画背景、曲线和光标。鼠标移动只重画光标；尺寸和窗口变化时重建背景与数据。实时滚动时，如果量程没变、时间只推进了少量列，就左移已有位图，再补右侧的新列；否则整幅重画。

位图左移也有拷贝成本。新列少，不代表整帧只花“一列”的代价。

## 启动后闪一下，是增量绘制写错了

这次检查页面时，曲线首帧能出现，随后几次刷新就消失。复现用的屏幕 `devicePixelRatio` 是 2。

画布的 CSS 宽度和实际位图宽度不同。例如页面宽 600 像素，位图宽 1200 像素，绘图上下文再用缩放变换保持 CSS 坐标。原来的自拷贝代码是：

```js
ctx.drawImage(canvas, -dx, 0);
```

这会按源位图尺寸绘制，又受到上下文变换影响，导致每次增量拷贝都再次放大。固定测试里，首帧有 6489 个曲线像素，第 3 次刷新归零。

修复时显式指定目标的 CSS 尺寸：

```js
ctx.drawImage(canvas, -dx, 0, cssWidth, cssHeight);
```

同时把数据层改为透明，避免遮住背景；透明位图的左移使用 `copy` 覆盖原像素，限制在绘图区内，再补画右侧。分数像素比例下关闭拷贝插值，避免反复平移把曲线越抹越宽。完整逻辑在 `js/engines/engine-canvas.js` 的 `_render`。

修复后，DPR 为 1、1.25、2 的连续八次增量刷新测试都通过。DPR=2 时曲线像素从 7257 变为 7205，没有再次消失；百万点实时流也检查了 66 次增量刷新，以及缩放和尺寸变化。这是显示正确性的回归，还不能说明长期运行的性能。

## 旧测量里有几项不能直接比较

此前留下的结果中，ECharts 调优版有接近 0ms 的更新耗时。查调用链后，这个数字只覆盖同步调用，没有等到下一次 rAF 执行实际的 `setOption`，不能解释成“渲染没有成本”。

Canvas 的同步刷新则会直接执行 `_render`，两者的计时终点不同。原稿拿这组数字比较快慢，还据此推算延迟增长，结论过头了。另一次测量期间显示器休眠，rAF 被节流，也不能引用它来证明 60fps。

每批更新耗时与批次间隔的比值，可以帮助判断处理能力是否吃紧。但只有在持续到达、逐批处理且不合并、不丢弃的队列中，处理速度长期低于到达速度才会持续积压。浏览器定时器会被阻塞，渲染也可能合帧；这个本地 demo 不能证明“运行 50 秒就落后 60 秒”。

页面上的 FPS 统计来自 rAF 回调频率；延迟的终点是绘制回调或 ECharts 的 `rendered` 事件。这些可以辅助排查，但都不是显示器实际呈现的精确时刻。旧性能结果也还没有在这次修复后重跑，所以这里不再保留速度倍数和设备适用范围的结论。

## 自己跑一次

项目没有构建步骤，ECharts 文件在本地。在项目目录启动静态服务：

```bash
python3 -m http.server 8765
```

打开 `http://127.0.0.1:8765/`，先跑单组，确认曲线持续显示，再比较实时窗口与全历史回看。要保留结果，用“导出 JSON”；比较时一起记录浏览器、DPR、窗口大小和页面是否在前台。

本次闪烁的回归入口是 `tests/canvas-regression.js`。在页面控制台执行：

```js
await (await import('./tests/canvas-regression.js')).runCanvasRegression();
```
