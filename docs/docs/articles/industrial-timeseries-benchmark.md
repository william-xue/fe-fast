# 一百万点的曲线，为什么在工业软件里就是画不出来

<div class="meta">
  <span>2026-10</span><span>·</span><span>约 12 分钟</span><span>·</span>
  <span>配套可运行基准：<a href="../bench/" target="_blank" rel="noreferrer">在线跑一遍</a></span>
</div>

工业软件里有一类需求长得几乎一模一样：几十路测点、几小时运行历史、秒级实时刷新，还要能 Zoom 到任意时间段回看故障瞬间。

客户拿通用图表库做完，Demo 阶段一切正常；上线三个月后，值班人员开始抱怨"画面比现场慢一分钟"。

这篇文章只讲一件事：**慢一分钟不是感觉，是可以算出来的。**

## 结论先行

- 朴素写法在 **10 万点**就已经负债运行：单次更新 104ms，数据每 50ms 来一批 → 负载率 **2.2**
- 负载率 > 1 意味着消费慢于生产，延迟随时间线性增长 —— 这就是"慢一分钟"的全部机制
- 自研分层在 **100 万点** 单次更新 **1.2ms**；回看 3 小时全历史 **22.6ms / 27MB**
- 同条件 ECharts 回看全历史：**930ms / 316MB**

## 一、先算清"欠账"，再谈优化

实时图的本质是一条流水线：数据以固定频率到达（比如每 50ms 一批），前端必须在 50ms 内完成"更新并上屏"。定义：

```
负载率 = 单次「接收 → 完成更新」的主线程毫秒数 ÷ 数据到达间隔
```

| 负载率 | 含义 |
|---|---|
| < 0.3 | 宽松，还能同时做别的事 |
| 0.6 – 1.0 | 临界，任何一次长任务都会开始堆积 |
| > 1 | **消费慢于生产，队列单调增长，延迟按秒级累积** |

跑 50 秒后，你看到的画面就是 60 秒前的数据。这和它是否重连、是否去重、是不是 WebSocket 都没关系。

## 二、三种写法，同一份数据

同一台机器、同一份合成工况数据（6 路信号、含越限尖峰）、同一个 60 秒可视窗口、每批 20 点 / 50ms：

| 后端 | 10 万点 | 100 万点 | 负载率 p95 |
|---|---|---|---|
| ECharts 朴素（全量 `setOption`） | **104.2 ms/次** | 未测（会失去响应） | **2.22** |
| ECharts 调优（LTTB + rAF + 只喂窗口） | ≈0 ms | ≈0 ms | ≈0 |
| 分层 Canvas（自研） | 0.5 ms | 1.2 ms | 0.024 |

::: warning 一个必须说清的测量陷阱
ECharts 调优那列的 `≈0 ms` 不是"它和自研一样快"，而是 **`setOption` 内部异步渲染，同步返回就是 0**。

我在基准页面里单独保留了这一点：用"接口调用耗时"评估渲染库，你会得到一张漂亮且完全错误的性能表。
要测就测到 `rendered` 事件，或测端到端上屏时刻。
:::

## 三、真正拉开差距的是"回看全历史"

实时流这组，调优后的 ECharts 其实能打平。但工业现场的日常动作不是盯着实时曲线，而是
**"把昨晚 2:13 那次跳闸拉出来看"** —— 视窗从 60 秒拉到 3 小时，一次性面对整段历史。

| 后端 | 10 万点 | 30 万点 | 100 万点 | 堆（100 万） |
|---|---|---|---|---|
| ECharts 调优（lttb） | 94.4 ms | 248.7 ms | **930.2 ms** | 316.3 MB |
| 分层 Canvas（自研） | 7.5 ms | 7.4 ms | **22.6 ms** | 27.6 MB |

原因不在"谁画得快"，在**谁还需要重新处理数据**：

- **自研**：历史一直是 `Float64Array`，回看只是把它聚合一次成 1158 列（O(n)，22.6ms）。
  之后无论怎么缩放、拖动，都只在这 1158 列上操作，不再碰原始数据。
- **ECharts**：要重新构造 100 万个 `[t, v]` 对象数组再全量 `setOption`。
  耗时随点数线性涨，内存从 78MB 涨到 316MB；用户体感是一秒白屏加之后的 GC 抖动。

一秒白屏在 Demo 里不算什么，在调度大屏上就是"这软件真卡"。差距就在这里。

## 四、四个把成本换掉的套路

### 1. 环形缓冲，替掉 `push` + `shift`

```js
// 常见死法
arr.push(point);
if (arr.length > N) arr.shift();   // O(n) 搬迁，每 50ms 一次，GC 跟着抖

// 换法：定长 typed array 环形缓冲
const buf = new SeriesBuffer(N);   // Float64Array 存时间，Float32Array 存值
buf.push(t, v);                    // O(1)，零分配，内存是一条直线
```

### 2. 列栅格：让成本与点数解耦

屏幕上只有约 1200 个像素列。把时间轴切成像素列，每列只保留四个数：最小、最大、第一个、最后一个。

- 100 万点 → 1160 列 → 画 1160 段，而不是 100 万个点
- **用 min/max，不用均值或抽样**：工业关心的是尖峰（越限、冲击、故障瞬间）。
  均值会把单点尖峰抹平，抽样可能整个漏掉。min/max 保证"只要发生过，就一定画得出来"

实测：10 万点和 100 万点的单次绘制代价只差 2.4 倍，因为画的东西一样多。

### 3. 脏区增量绘制：一帧只画一列

直播时时间轴单调向右滚动，上一帧的位图 99% 仍然有效。

```js
ctx.drawImage(canvas, -dx, 0);        // 整幅左移
ctx.clearRect(w - dx, 0, dx, h);      // 清掉右侧新露出的条带
drawColumns(nCols - shift, nCols);    // 只补这一列
```

这一条在办公室里看不出价值，在现场机器上是决定性的：我在**无 GPU 的软件光栅环境**里测过，
整幅重绘 1236×357 的画布要 ~65ms/帧，帧率从 60 掉到 15；改成增量绘制后回到 vsync。

工控机、远程桌面、虚拟机里跑大屏的项目，卡不卡往往就差这一层。

### 4. 分层 + rAF 合帧

- 背景层（网格、坐标轴、刻度）：只在尺寸或窗口变化时重画
- 数据层（曲线）：按上面的增量策略刷新
- 光标层（十字线、读数框）：只在鼠标移动时重画

同时用 `requestAnimationFrame` 合帧：一帧内到达的多批数据只渲染最后一次。
WS 推 20 次/秒、屏幕刷 60 次/秒，中间的差应该被合并，而不是排队。

## 五、ECharts 到底还能不能用

能，而且大多数场景应该继续用。它的边界很清晰：

- **10 万点以内的静态图表**：调参（`sampling: 'lttb'`、关动画、`dataZoom`）足够，不必自研
- **流式实时图**：可以用，但必须接受两个前提 —— 只喂可视窗口，渲染与到达频率解耦
- **百万点 + 多路 + 长历史回看 + 现场弱机器**：这时会同时撞上三堵墙 ——
  `setOption` 的全量 diff、`[t,v]` 对象数组的内存与 GC、整幅重绘的合成器成本。
  换库解决不了第三堵

## 六、怎么判断你面对的系统

不必相信任何人的 benchmark，包括这篇。三个动作就能定性：

1. 给每条数据打**产生时刻**，前端记录**上屏时刻**，日志输出 `lag = 上屏 − 产生` 的分位数。
   一分钟级的滞后会立刻现形。
2. 算**负载率**：抓一段时间内的单次更新耗时 ÷ 到达间隔。> 1 就是负债运行。
3. 关掉 WebSocket 只留本地合成数据再跑一遍。还慢 → 问题在渲染；立刻好了 → 问题在链路和背压。

这三步做完，你要么修好了一个真问题，要么发现根本没有渲染问题 —— 两种结果都比继续换图表库有价值。
